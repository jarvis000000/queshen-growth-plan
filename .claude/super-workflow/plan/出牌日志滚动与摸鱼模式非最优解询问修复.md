### BUG1 根因（已实测确认，非推断）

视口 1280×800 下量取（18 手出牌后）：

| 元素 | scrollTop | scrollHeight | clientHeight | 实际可滚动量 |
|---|---|---|---|---|
| `.plain-log`（代码滚动对象） | 0 | 2058 | 2058 | **0** |
| `.plain-page`（真实滚动者） | 563 | 2280 | 800 | 1480 |
| `.plain-inner` | — | 2280 | 2280 | — |

- `.plain-inner` 只写了 `min-height: 100%`（**只有下限没有上限**），被日志内容撑高到 2280px；
- `.plain-log` 随容器长到 2058px，`clientHeight === scrollHeight` ⇒ **从不产生内部溢出**，`overflow-y: auto` 形同虚设；
- 于是 `push()` 里的 `el.scrollTop = el.scrollHeight` 作用在 `maxScroll = 0` 的元素上 —— **空操作**；真正在滚的 `.plain-page` 代码从未触碰；
- 副作用：日志一长，输入框被顶出视口（page 2280 / 视口 800），需手动滚下去才能打字。

### D1 方案（主人裁定：恢复「日志区自身滚动」）

1. `.plain-inner`：`min-height: 100%` → **`height: 100%`**，给 flex 容器确定高度，日志区才能成为真正滚动容器。
   - 「窗口过矮」兜底**仍然成立**：非日志内容 + 日志 `min-height: 5em` 超出容器时子元素照旧溢出，由 `.plain-page` 滚动，不裁切。
2. `push()` 的滚动抽为 `scrollToEnd()`：先滚日志区自身，再滚 `.plain-page`。短窗口下由外层页面承担滚动，只滚内层末行仍会留在视口外，故两者都滚；常规情况下外层赋值自然是空操作。

### D2 方案（复刻图形界面的拦截询问流）

`App.vue:98-121` 已有成熟询问流，摸鱼模式改为同构实现，不新造判定逻辑：

| 步骤 | 实现 |
|---|---|
| 新增状态 | `const pendingDiscard = ref<number \| null>(null)`（待确认的牌） |
| `tryDiscard` 改 async | 守卫不变 → 出牌前取 `adviceDiffFor(tile)` 快照（`commitDiscard` 会清空 `advice`）→ `await store.requestDiscard(tile)` |
| `needsConfirm === false` | 已由 store 打出，清空 `pendingDiscard`；沿用原有「与最优解相差 N 分」dim 教学 |
| `needsConfirm === true` | **不打出**，置 `pendingDiscard`，push 差距提示 + 命令提示 |
| 方向键候选 | `navigableCommands()` 在待确认态优先返回 `[打出, 查看建议, ...可打出的牌]`（`打出`/`查看建议` 排最前便于立即选中，同时保留选牌能力以支持「再选牌重打」） |
| `打出` | `commitDiscard(pendingDiscard)`，日志记 `你打出 X` |
| `查看建议` | `printComparison(pendingDiscard)`：**基于全量候选折算胜率后筛行**，展示原牌 + 前 3 名（由 `i < 3 \|\| tile === focusTile` 天然去重），并把原牌标注为「你原本要打的」 |
| 看完建议 | **保留待确认态**：仍可 `打出` 确认，也可直接选别的牌（走 `tryDiscard` 重新判定）——避免重打同一张时反复弹同一提示 |
| 命令词 | 抽常量 `DISCARD_CMD = '打出'` / `ADVICE_CMD = '查看建议'`，消除魔法值 |
| 重开 | 清空 `pendingDiscard`，避免遗留状态卡住 |

**关键约束（易错点）**：`relativeRates` 是按**传入集合**归一化的（`engine/ai.ts:171-177`）。要展示「原牌 + 前 3 名」时必须传入**全量候选**、筛掉不展示的**行**；若直接传子集，胜率会被重新归一化而失真。

### 复用的既有资产（DRY）

### 评级口径（三档，复用既有阈值，不新增魔法值）

在 `commitDiscard` 内、`advice` 被清空前评级：

```
建议缺席            -> unrated   （计入总手数，不参与三档分母的判定）
adviceDiffFor 为 null -> best      （打出的即最优，或仅一张可打）
significant 为真     -> blunder   （gap >= 12，即会触发拦截的明显劣化）
其余                -> acceptable
```

- 与 `adviceAlert` 开关**正交**：`adviceAlert` 只决定是否提示，评级始终进行。
- 总手数 = 四类之和（**不额外存 `hands` 字段**，避免冗余状态漂移）。

### 净分口径（必须如实告知主人）

引擎只记录赢家分数、无分家结算，故：

```
流局                      -> +0
winners[0].seat === 人类   -> +score.total
winners[0].from === 人类   -> -score.total   （放炮）
其余（他家胡、非人类放炮）   -> +0

## （原始误判过程）

验证期间发现 `tests/store.spec.ts > 玩家出牌后进入他家行动流程` **间歇性失败**（隔离跑约 1/3，全量跑约 2/3）。

```
出牌前：canDiscard=true, awaiting=true, hand 17 张且含该牌
同步后：canDiscard=false        ← commitDiscard 确实成功了
2.5s 后：handLen 16 / discards=[]  ← 牌离手却从未进弃牌堆
```

**机制**：上一局的旧循环未死透时，其 `decideDiscard(HUMAN_SEAT)` 读取的是 **`state.value`（当前这局）** 而非循环自己捕获的 `game`，于是把 `awaitingHumanDiscard = true` 与 `discardResolver` 装到**新对局**上；玩家出牌喂给了旧循环的 resolver，旧循环醒来后撞上 `gen !== generation` 检查**丢弃该牌**；新对局自己的等待已被覆盖，人类那手永远打不出去。

**为什么判定为既有缺陷（非 R4/R5 引入）**：
1. `decideDiscard` 读取 `state.value`、以及 gen 检查位于 `decideDiscard` **之后**（`stores/game.ts:223-224`）——两处本轮均未改动；
2. 该窗口只由「快速连续 `start()`」触发，与本轮新增的报听标志、白板归位均无关（诊断现场 `declaredReady=false`、`followHand=null`）；
3. 触发条件是**快速连续重开**——`tests/store.spec.ts` 的既有测试模式，真人也可能连点「再来一局」撞上。

**影响**：使全量测试结果不稳定（单次跑通不能证明无回归）；真实用户连点重开可能遇到「轮到自己却打不出牌」。

⇒ 属 R5 范围之外，已提请主人裁定是否修复。

APPLY_AFTER seat=0              disLen=1 handLen=16      ← push 成功，长度就是 1
```

push 确实成功，随后长度又回到 0 ⇒ 一定有代码把它拿走。全量搜索 `discards` 后命中 `engine/game.ts:252-254` 的 **`reclaimDiscard`**：**对家吃/碰/杠走这张牌时，牌会从打出者牌河中被合法取走**。

⇒ 所有观测（手牌 17→16、`discards` 为空、`lastDiscard/lastDiscardSeat` 已写入、对局继续推进）**完全自洽**，是标准麻将行为，**不是缺陷**。

**真实问题**：既有测试 `玩家出牌后进入他家行动流程` 断言「打出的牌留在自己牌河里」，只要对家吃碰杠就必然失败（概率约 1/2–2/3）。

**处置（全部完成）**：

## Phase 1 Plan

### 根因（代码引证，非推断）

`findClaims` 对**每一个**可行组合各产出一条 `ClaimOption`：

- `src/engine/game.ts:192-194` —— 吃的每个组合各 push 一条 `{ seat, kind: 'chow', tiles: combo }`
- `src/engine/meld.ts:97-106` —— `findChowOptions` 对 3 种牌型模板逐个尝试，**每种成功都产出 1 项** ⇒ 同一座位可产出 1–3 条 chow 条目

而 `resolveClaims` 的循环对**每一条** `seat === HUMAN_SEAT` 的条目都调一次询问：

- `src/stores/game.ts:440-450`：

```ts
for (const claim of ordered) {
  if (claim.seat === HUMAN_SEAT) {
    if (human.value.declaredReady) { /* 报听分支 */ }
    const accepted = await askHumanClaim(ordered)   // ← 逐条再问一次
    if (accepted) return executeClaim(accepted)
    continue
  }
  ...
}
```

**⇒ 玩家有 3 种吃法时，第一次「过」之后会立刻被再问一次（共 2 次），因为循环推进到了下一条属于玩家的 chow 条目。** 同时能碰又能吃时同理（碰 1 条 + 吃 N 条）。

注：`askHumanClaim` 内部已用 `all.filter(item => item.seat === HUMAN_SEAT)` 把**全部**玩家选项一次性放进 `claimPrompt.options`，所以提示内容本身是全的——**缺陷只在「问了几次」，不在「问了什么」**。

### 方案（最小实现）

在循环内记录「玩家是否已被询问过」，同一张打牌只问一次：

```ts
// 吃有多种组合会为同一座位产出多条响应，但玩家只该被问一次
let askedHuman = false
```

在玩家分支内，非报听时 `if (askedHuman) continue` 后再询问。

**为什么不是「先把玩家选项合并成一条」**：`claimPrompt.options` 必须保留多条 chow 条目，玩家才有「选哪种吃法」的可能；合并会丢掉这个能力。缺陷只在询问次数。

**为什么优先级顺序不被破坏**：`ordered` 按 `CLAIM_PRIORITY` 降序稳定排序，玩家条目中**最先出现的那条**就是其最高优先级响应；在那一轮询问即可，后续同座条目跳过。AI 一侧仍按组合逐条评估（`shouldClaim` 需要逐种吃法比较），保持不变。

### 口径定稿（可核算）

**单家得分 S**（即「本局得分」，主人所说的「单家的输赢的分」）：

```
S = BASE(1) × ∏ 倍数 + 财神张数 × 1
```

| 倍数项 | 触发 | 值 |
|---|---|---|
| 硬胡 | `isHardWin` 为真（未用财神当万能牌） | ×2 |
| 自摸 | 自摸胡 | ×2 |
| 连庄 | 当前连庄次数 n（n=0 时不适用） | ×2ⁿ |
| 清一色 | `flushInfoOf().pure` | ×2 |
| 对对胡 | `isAllTriplets` | ×2 |
| 杠开 | 开 1 杠后补牌自摸胡 | ×2 |
| 二连杠 | **连续**开 2 杠后胡 | ×4（取代杠开，不叠乘） |

**四家结算（边金额规则：只要这条边的两端有一端是庄家，该边金额 ×2）**

| 场景 | 结算 |
|---|---|
| 自摸（赢家 W） | 对每个 `P ≠ W`：`额 = (P 是庄家 ‖ W 是庄家) ? 2S : S`，`P -= 额`、`W += 额` |
| 点炮（赢家 W、放炮者 D） | `额 = (D 是庄家 ‖ W 是庄家) ? 2S : S`；`D -= 额 + 1`、`W += 额 + 1`；另两家 0 |
| 明杠 / 加杠（杠家 K） | 其他三家各 `-1`，K `+3`（**固定值**） |
| 暗杠（杠家 K） | 其他三家各 `-2`，K `+6`（**固定值**） |

## Phase 1.5 主人中途更正（**重要，已并入实现**）

> 一张财神 +1 分　明杠 其他家 −1（+3）／暗杠 −2（+6）　放炮者额外 −1 给赢家
> 「这里的 1 是以底数为 1 的情况下。底数为 2 应该改成 2」

**解读**：上述的 `1` 不是绝对分值，而是**「一份」**，随底分缩放。故实现必须把耦合关系写进代码，而非硬编码数值：

```
一份 = BASE_SCORE × 系数
```

| 规则 | 系数（`UNIT`） | 底分 1 时 | 底分 2 时 |
|---|---|---|---|
| 每张财神 | `JOKER = 1` | 1 | 2 |
| 明杠 / 加杠：其他每家 | `EXPOSED_KONG = 1` | −1（杠家 +3） | −2（杠家 +6） |
| 暗杠：其他每家 | `CONCEALED_KONG = 2` | −2（杠家 +6） | −4（杠家 +12） |
| 放炮者额外给赢家 | `DEAL_PAYER = 1` | −1 | −2 |

**设计处置**：新增 `UNIT` 系数表与 `shareScore(份数)`（`score.ts`）。杠家所得**由其他三家之和推出**（3 × 一份），不另设 `+3` 常量——既零和自洽，又让「一份」只有一个真相源。

# Round 10（主人报障：吃碰时该用白板，却花掉了财神）

## Phase 0 根因（代码引证）

`findChowOptions` → `takeIndex`（`engine/meld.ts`）的取牌顺序写反了：

```ts
for (...) { if (hand[i] === need) return i }              // 先精确匹配
if (whiteActsAsJokerTile(jokerTile) && need === jokerTile) { /* 白板回退 */ }
```

因为当 `need` **恰为财神本色**时，财神牌本身就等于 `need` ⇒ 第一个循环必然先命中财神牌，白板那一段成了**不可达代码**。`collectSupport`（碰/杠取牌）复制了同一套顺序 ⇒ 同样中招。

## 判据（为什么白板优先才对）

白板**只能**充当财神本色；财神牌是万能牌，还牵动硬胡判定与财神分。手牌同时有两者时，用白板去顶该本色、把万能牌留在手里**严格更优**。

| 改动 | 说明 |
|---|---|
| `takeIndex` | 白板那一段提到精确匹配**之前** |
| `collectSupport` | 改为复用 `takeIndex` 逐张取，消除重复的优先级规则 |
| 新增 `actsAs()` | 让 `countSupport` 与取牌口径同源（原先两处各写一遍等价规则） |
